# V9 数据库全面审查与整改清单（2026-10-27）

## 检查范围与基础版本

基于 `huangren` GitHub V8（提交 `44e0aa6`）审查了：V5 布局模板 JSON、V6 任务/审核记录 JSON、Excel SKU 逐行制图、Streamlit 页面状态、数据写入和备份方式。没有接入任何客户私有业务数据库或第三方云服务。此次新增 SQLite 数据层，以旧版本机 JSON 作为用户**可选择迁移**的数据源。

## 主要问题与本次处理

| 风险 | 原情况 | V9 处理 | 留存风险 |
| --- | --- | --- | --- |
| 记录散落 | 模板和任务分散在 JSON 目录 | 用五张 SQLite 表保存业务元数据 | 既有文件需用户显式迁移 |
| 多窗口覆盖 | JSON 保存无统一版本控制 | SQLite 事务与任务乐观版本号 | 无多人登录/角色隔离 |
| 旧审核丢失 | 新审核覆盖任务当前摘要 | 追加 `review_events` 和图片哈希 | 有系统文件写权限者仍可篡改 DB |
| 模板重名 | 依赖文件名和文件系统大小写特性 | 数据库 `name_key` 唯一约束，大小写不敏感 | 原旧模板不自动进入新库 |
| 备份不一致 | 文件复制不保证包含 WAL 状态 | SQLite 在线备份 API，备份前后检查 | 需要定期在可信存储保留副本 |
| 恢复误覆盖 | 没有正式的恢复操作流程 | 先验证备份，显式 `--overwrite --app-stopped`，检查 WAL/SHM | 不能完全检测外部进程正在使用 DB，操作员必须停止程序 |
| 旧记录迁移风险 | 可能同名、损坏或重复导入 | SHA256 导入日志，逐文件原子提交，不删除源文件 | 原文件修改后冲突需人工处理 |
| 敏感数据 | 产品图和接口密钥不应持久化 | 严格字段白名单，不存图像字节/API Key | 审核人标识、商品文件名仍是受保护信息 |
| 图片与审核脱节 | 只看任务状态容易误判 | `job_files` 校验和审核事件绑定 SHA256 | 不能保证图片肉眼结构正确，仍需人工验收 |

## 已验证

- 旧版离线制图、AI 返回校验等回归测试；
- 新数据库初始化、写入和读回、任务不可变字段约束；
- 历史审核追加、旧窗口更新冲突、事件摘要篡改检查；
- 蓝白/黄黑/灰白布局 JSON 序列化与重名限制；
- 旧版 JSON 导入、重复导入、损坏与更改冲突处理；
- 数据完整性扫描、SQLite 外键约束、备份后恢复并重新读取；
- CLI 初始化、检查、备份、恢复的命令行演练。

## 尚未达到的能力

1. **多人共用**：不具备账号认证、角色权限、审批分级；不建议把单机 SQLite 直接部署成公共多人编辑服务。
2. **审计抗篡改**：SHA256 校验不是加密签名；具备文件读写权限的人能够修改数据库与事件记录。
3. **跨设备同步**：本地库不会随 GitHub 代码同步到其他电脑，也不应放在多台电脑同时写入的共享盘。
4. **真实运营数据迁移**：本次未获得用户电脑 `.local` 目录，因此未迁移任何用户的真实历史记录。
5. **生产浏览器验收**：CI 不等于真实环境/真实商品图的交互验收；应在目标电脑实际确认导入、审核、备份下载和恢复流程。

## 运营建议

首次升级时先备份整个 `.local`，再按 [数据库迁移与备份说明](database-v9.md) 执行迁移。任务库与原商品图/审核 ZIP 分开备份。在三种 SKU 模板各跑至少一批真实产品样本，并安排真人复核尺寸和产品结构后再投入日常生产。所有审核通过标记均是流程记录，不等于平台官方检测认证。
