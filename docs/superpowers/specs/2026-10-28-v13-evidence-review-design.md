# V13 参数证据审核工作流设计

## 意图

把第四阶段做成仓库现有 Streamlit 中文应用中的一个工作页。运营或资料审核人员输入制造商型号和参数关键词后，可以并排检查原始资料片段、页码/单元格/行号、PDF 区域预览、已有参数主张和未解决冲突，再由人工明确创建候选主张、提交复核或处理冲突。

## 当前结构与设计决定

仓库已有 V13 的 append-only 来源、参数主张、证据、复核、状态事件和冲突表；知识库数据库触发器已限制 accepted 主张必须有支持性证据和独立支持性复核。V13 文档索引已保存 PDF bbox、DOCX 段落/表格位置、Markdown/TXT 行号、Excel 工作表和单元格范围。现有应用使用 Streamlit，故在 app.py 增加一个标签页，而不是再引入第二套 Web 框架或新数据库。

服务层放在 src/ecom_images/knowledge_review_v13.py，负责只读工作区查询、来源校验、PDF 页预览、候选主张和证据的原子写入、复核及状态变更、未解决冲突列表。界面层只调用服务 API，继续使用 DEFAULT_DB。

## 工作流

1. 初始化/检查 V13 与文档索引；可在界面上传单个受支持文档（100 MiB 上限、扩展名白名单、临时副本自动清理），也可继续使用现有 CLI 导入；随后输入精确型号及参数关键词。
2. 展示原始资料结果及已有主张。每条结果显示文件名、SHA-256、来源等级、原文、物理 PDF 页码或 DOCX/Markdown/Excel 定位信息。
3. 对 PDF 按登记的源文件 SHA-256 重新校验后渲染页图，并在原始 bbox 上叠加高亮框；来源缺失或被篡改时不展示为可信预览。
4. 审核人员显式选择已登记的制造商型号、填写参数原始值/单位/录入人，再将选定片段与候选主张、来源证据在一个 SQLite 事务中创建；不自动绑定 SKU。
5. 复核表单追加审核意见；如请求接受主张，数据库既有门槛必须通过。接受失败时整次复核与状态变更回滚，不能留下半提交状态。
6. 展示未解决冲突；只有选定已有来源并填写书面处理说明，才允许将冲突标记为解决。

## 方案比较

- 方案 A：在现有 Streamlit 应用内新增审核标签页，并把事务性逻辑放入独立服务模块。采用此方案，因为它复用现有 UI、DEFAULT_DB、V13 触发器和文档索引。
- 方案 B：只增加命令行审核命令。改动少，但无法满足原文页预览与可视化审核的目标。
- 方案 C：另建独立 Web 应用和新数据层。会重复已有数据库门槛并增加迁移/部署复杂度，因此不采用。

## 目标与非目标

目标：可在本地界面导入文档、可搜索、可回溯、可人工复核、可查看未解决冲突；原始文件指纹与历史记录保留；操作可自动化测试。

非目标：OCR、自动推断/接受参数、自动建立 SKU 映射、制造商身份认证、用户账号/权限系统、修改 V13 schema 或导入用户私有资料到 GitHub。

## 安全和正确性约束

- 所有写入使用现有 append-only V13 表；不 UPDATE/DELETE 既有知识记录。
- 在生成 PDF 预览或由索引片段创建证据前，核对存储文件 SHA-256 与来源登记值。
- PDF 页码是物理页码；其他文件不伪造 PDF 页码，位置写入 region JSON。
- 原始片段只是证据候选，不自动代表参数正确。
- 只有显式选择制造商型号 ID 才能创建该型号的参数主张；同名 SKU 文本不会自动成为型号映射。
- 接受/解决动作必须保留人工身份、方法/理由和数据库既有门槛。

## 验收

- 单元测试覆盖原子创建、原始文件篡改阻断、PDF bbox 预览、接受门槛、反对意见重开、冲突筛选/解决来源约束。
- Streamlit 标签页接入有回归测试。
- GitHub Actions Python 3.10 和 3.12 全量测试通过。
